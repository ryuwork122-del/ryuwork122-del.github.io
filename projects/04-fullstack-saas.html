Multi-Tenant SaaS App

A production web application with role-based access, Stripe billing, background jobs and an audit trail — built to survive real traffic and real edge cases.

The problem

The product began as a single-tenant tool for one customer and had to become a self-serve service for many. That is not a feature addition — it is a change to almost every query, every permission check and every assumption about who owns a row.

Approach

Tenancy is modelled explicitly: every business table carries an organisation_id, and database row-level policies enforce that a request only ever sees rows belonging to its own organisation. The application filters as well, but the database policy is the backstop — one forgotten WHERE clause should not become a data leak.

Roles are owner, admin and member, with permissions expressed as a small capability matrix rather than role checks sprinkled through the code. Adding a role or moving a capability is a one-line change in one file instead of a hunt through every handler.

Billing runs on Stripe with the webhook as the source of truth. Checkout redirects are fast and optimistic, but entitlements are only ever granted by a verified, idempotent webhook — otherwise a dropped redirect silently gives away a paid plan.

On the front end, React with TypeScript shares validation schemas with the server so the client and API agree on what a valid payload is. Slow work — exports, emails, report generation — is queued to a background worker and surfaced as a job the user can watch, instead of a request that eventually times out.

What was hard

Caching. Per-tenant data behind a shared cache key is the classic way to serve one customer another's page. Cache keys now include the organisation and the permission scope, and anything permission-sensitive is simply not cached.

Webhook ordering was the other trap. Stripe events can arrive out of order, so each handler is idempotent and reconciliation compares against the subscription's current state rather than assuming events arrive sequentially.

Outcome

A single deployment serves many isolated organisations, onboarding is self-serve, and every privileged action is written to an audit log with the actor, timestamp and before/after values. The patterns that started as safety measures turned out to be the features customers asked for first.

Takeaways

Enforce isolation at the lowest layer you can, treat webhooks as the only truth for billing, and make the audit log a first-class table instead of an afterthought.
