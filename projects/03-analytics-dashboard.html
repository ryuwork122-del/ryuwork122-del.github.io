Analytics Command Center

A warehouse-to-dashboard pipeline that turns messy operational exports into a single live view of funnel, retention and revenue health.

RoleData engineering & analysis
Year2025
TypeReporting platform
StackSQL · dbt · pandas · Power BI
Replace with a screenshot: assets/03-cover.png

The problem

Reporting ran on a spreadsheet that had been copied forward for years. Every question — how many trials converted, which cohort retained, what this month's revenue actually was — needed a fresh manual export and a few hours of formula surgery. Two people running the same query got different numbers, and nobody could explain why.

Approach

First, definitions. Before writing a pipeline I wrote down what each metric means in plain language — what counts as an active user, when a trial becomes a customer, how refunds are handled. That document is the actual deliverable; the SQL just implements it.

The pipeline lands raw source exports in a staging schema with no transformation at all, so the original data is always recoverable. From there, dbt models clean and deduplicate into staging views, join into conformed dimensions and facts, and finally expose a small set of mart tables shaped for the questions people actually ask. Every model has tests: unique keys, not-null constraints and referential checks between facts and dimensions.

pandas handles the parts SQL is awkward at — irregular date parsing, fuzzy matching of customer names across systems, and one-off reconciliation — and writes its results back into the warehouse so everything downstream reads from a single source of truth.

The front end is Power BI on a star schema: three report pages (acquisition funnel, retention cohorts, revenue) with consistent date filtering and drill-through to the underlying records.

What was hard

Duplicate customers. The same organisation existed under three spellings across two systems, and simple joins multiplied rows and quietly inflated revenue. Matching needed normalisation, blocking on a shared key and a review queue for ambiguous cases — with the match decisions stored so they are reproducible rather than baked into an ad-hoc query.

Time zones came second. Timestamps were recorded in local time without an offset, which made "daily" meaningless across regions. Everything now lands in UTC at ingestion and converts only at the presentation layer.

Outcome

The metrics are defined once in tested SQL, so the same question gives the same answer whoever asks it. Refreshes run on a schedule, report builders work from a documented star schema instead of raw exports, and data quality problems surface as a failing test before they reach a chart.

Takeaways

Most analytics problems are definition problems wearing a technical costume. Write the metric definitions down, test them in code, and the dashboards almost build themselves.
