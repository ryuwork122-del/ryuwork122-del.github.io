Godot Action Prototype

A fast, responsive 2D action game in Godot — hand-tuned movement, state-machine enemies and a custom shader pass for lighting.

RoleDesign & programming
Year2026
TypePersonal project
StackGodot 4 · GDScript · Aseprite

The goal

I wanted to understand why some action games feel good and others feel like moving a cursor. The answer is rarely the art — it is input handling, acceleration curves and feedback timing. So I set out to build one small, tight combat loop and tune it until it felt right.

Approach

Movement comes first and gets the most attention. The player has separate acceleration and deceleration rates, a coyote-time window after leaving a ledge, and a jump buffer that remembers a press made slightly too early. None of these are visible in a screenshot; all of them are the difference between responsive and mushy.

Enemies are finite state machines — idle, patrol, alert, chase, attack, stagger — with explicit transitions and no logic in the animation tree. Each state is small enough to read in one screen, which made debugging behaviour dramatically easier than a tangle of conditionals.

Combat relies on frame-accurate windows: attack startup, active and recovery phases, with hitboxes enabled only during the active frames. Hit-stop briefly freezes the action on impact, and screen shake is applied through a noise-based camera offset that decays — subtle, and the single biggest contributor to how hits feel.

Lighting is a custom shader pass: a light mask is rendered to a separate viewport, blurred, and composited over the scene to give the 2D art depth without a normal map for every sprite.

Level content, enemy stats and attack timings live in resource files rather than in code, so tuning a value does not mean touching a script.

What was hard

Coupling. Early on, movement read the attack state and the attack state moved the player, and bugs multiplied at the intersection. Separating intent (what the input wants) from state (what the character is doing) fixed a whole class of problems at once — the same decoupling I lean on in application code.

Shader performance on low-end hardware was the second lesson: the blur pass was cheap on my machine and not on integrated graphics, so resolution and iteration count had to be scaled by a quality setting.

Outcome

A playable vertical slice with a combat loop that feels deliberate rather than approximate, a content pipeline that non-programmers could tune, and a much better instinct for what "game feel" actually means in numbers.

Takeaways

Responsiveness is a data problem before it is a code problem — measure the frames, tune the curves, and let the player feel the difference.
